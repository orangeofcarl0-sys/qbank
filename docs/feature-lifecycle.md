# 功能生命周期

qbank 使用“先定义契约、再实现、最后验证同步”的功能生命周期。

## 1. 提议

新功能进入 `0.3.0`，实现前必须满足以下任一条件：

- 建立 `docs/features/<feature>.md`；或
- 建立包含同等字段的可审查 issue 摘要，并在实现 PR 中补齐功能文档。

从 [功能模板](features/_template.md)开始，说明用户目标、入口、数据变化、安全边界、
兼容性和验收方式。仅内部重构也要明确是否影响公共行为。

## 2. 设计

核对 [文档地图](documentation-map.md) 和 [兼容性策略](compatibility-policy.md)。
涉及架构边界、数据权威来源、事务、安全或依赖变化时，在 `docs/adr/` 新增 ADR，记录
上下文、决定、替代方案和后果。

## 3. 实现

- 保持领域模型、应用服务、基础设施和界面的依赖方向。
- CLI、Studio 与 MCP 复用相同应用语义，不复制业务规则。
- 写操作必须先 dry-run，并保留确定性失败行为。
- 示例只使用自制合成数据。

## 4. 文档同步

根据 [维护策略](maintenance-policy.md)逐项更新受影响文档。公共 CLI 或 MCP 能力必须进入
相应参考；Schema 或配置变化必须说明迁移；用户可见变化必须进入 CHANGELOG。受管用户文档
按[本地化策略](localization.md)同时更新简体中文和英文版本，不在单篇正文中混合解释性语言。

## 5. 验证

运行文档同步门禁、完整质量门、相关 wheel 安装测试和必要的真实交互验收。删除功能时
还要验证旧入口的弃用或失败行为，避免留下隐藏能力与失效文档。

## 6. 发布与维护

- 已发布的 `v0.2.0` tag 保留其原始版本含义，后续修复以新补丁版本发布。
- 阻断性兼容修复基于 `release/0.2`，版本为 `0.2.1`。
- 新功能目标版本为 `0.3.0`。
- 软件版本与 Question、Asset、Paper Schema 版本独立；任一方变化都要单独记录。

功能完成后，功能文档状态应从 `proposed` 更新为 `implemented`，并填写实际测试、限制和
迁移结论。被撤回或替代的设计保留历史记录并标记状态，不直接删除背景。
